# Backend Integration Guide for Zonomo

This document explains how the frontend expects to communicate with the Spring Boot backend, specifically focusing on fetching service providers.

## 1. How `customerService.ts` is structured

The `services/customerService.ts` file acts as the bridge between the React Native UI and the backend API. Currently, it uses a mock setup that simulates the backend.

### Connecting the real backend

When your Spring Boot endpoints are ready, connecting them is a 1-minute task:

1. Open `services/customerService.ts`.
2. Locate the function (e.g., `getProvidersByCategory`).
3. Uncomment the API call block:
   ```typescript
   const response = await api.get(`/categories/${categoryId}/providers`);
   const backendData = response.data;
   ```
4. Delete the entire `const backendData = await new Promise(...)` mock block.
5. Save the file. The mapping logic below it will automatically handle the rest!

### Why do we map data?
The backend returns raw database-friendly data. The UI component needs UI-friendly data. We do this mapping inside the service file so the UI components remain clean.

**Backend Response Format:**
```json
{
  "id": "p_101",
  "name": "Rajesh Kumar",
  "rating": 4.8,
  "distance": "2.5 km away",
  "hourlyRate": 250
}
```

**Mapped Frontend Format:**
```json
{
  "id": "p_101",
  "name": "Rajesh Kumar",
  "initials": "RK", // Generated by frontend
  "serviceId": "elec", // Derived from request
  "serviceName": "Elec Professional", // Generated by frontend
  "rating": 4.8,
  "reviews": 120, // Currently mocked by frontend
  "distance": "2.5 km away",
  "price": "₹250/hr", // Formatted by frontend
  "isOnline": true, // Currently mocked by frontend
  "lastSeen": "1h" // Static fallback
}
```

## 2. What the Backend Needs to Implement

To make the Provider list work perfectly, your Spring Boot backend must implement this endpoint:

### `GET /api/categories/{categoryId}/providers`

**Path Variable:**
- `categoryId`: This will be passed exactly as the user selects it. It could be a specific subcategory (like `plumb`, `elec`) or `all` if the user wants all providers in a parent category (like `repairs-and-fixes`).

**Backend Responsibilities:**
1. **Filtering by Category:** Fetch providers associated with the given category/subcategory.
2. **Verified Only:** The backend MUST only return providers whose status is `APPROVED`. The frontend trusts the backend and automatically gives all returned providers a "VERIFIED" badge.
3. **Location (Optional but Recommended):** Ideally, the backend calculates the `distance` string based on the customer's lat/lng vs the provider's lat/lng. For MVP, you can return a hardcoded string like `"2.5 km away"`.

**Expected JSON Response (200 OK):**
```json
[
  {
    "id": "p_123",
    "name": "Rajesh Kumar",
    "rating": 4.8,
    "distance": "2.5 km away",
    "hourlyRate": 250
  },
  {
    "id": "p_124",
    "name": "Amit Singh",
    "rating": 4.9,
    "distance": "1.8 km away",
    "hourlyRate": 300
  }
]
```

### Next Steps for Backend Dev
1. Ensure the `Provider` entity in Spring Boot has fields for `name`, `rating`, and `hourlyRate`.
2. Create a repository method to find `Provider` where `status = 'APPROVED'` and `serviceId = :categoryId`.
3. If `categoryId == 'all'`, fetch all approved providers for the parent category.
4. Expose this via a REST Controller.

## 3. Categories and Subcategories Structure

The Zonomo frontend organizes services into primary categories and specific subcategories. The backend needs to understand this hierarchy to provide accurate data.

### Parent Categories
These represent the main tiles on the customer home screen (e.g., Repairs & Fixes, Cleaning, Personal Care).
- `repairs-and-fixes`
- `cleaning`
- `personal-care`
- `health-and-wellness`
- `care-and-assist`
- `relocation`

### Subcategories
Inside each parent category, there are specific subcategories (the chips at the top of the provider list).
For example, under `repairs-and-fixes`, the subcategories are:
- `elec` (Electrician)
- `plumb` (Plumber)
- `carp` (Carpenter)
- `ac` (AC Repair)

### How they interact
When fetching providers (`GET /api/categories/{categoryId}/providers`), the `categoryId` passed in the URL will typically be the **subcategory** ID (e.g., `plumb`). 
However, if the user selects the "All" chip, the frontend will pass `all`, and the backend should understand that it needs to return all providers under the currently active *parent* category (though currently the frontend just sends `all`, so the backend might need the parent category as a query param in the future, e.g. `GET /api/categories/all/providers?parent=repairs-and-fixes`).

For now, ensure your database links providers directly to these specific subcategory IDs (`elec`, `plumb`, `home`, `pest`, etc.) so they appear in the correct lists!
